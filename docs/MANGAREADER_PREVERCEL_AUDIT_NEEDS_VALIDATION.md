# NEEDS VALIDATION — Prioritized leads (no severity; not confirmed vulnerabilities)

## 1. auth/refresh.no-origin-check.samesite-sibling-subdomain

**Claimed root cause**: src/app/api/auth/refresh/route.ts performs no origin validation (the only cookie-authenticated mutation of the auth trio without assertSameOrigin) while authenticating solely by the SameSite=Lax, path=/api/auth, host-only tsundoku_rt cookie; SameSite=Lax withholds the cookie only on cross-SITE requests, so a sibling-subdomain page (same registrable domain, cross-origin) can invoke the state-changing rotation in the admin's browser.

**Verified evidence**: refresh handler has no origin check (imports omit assertSameOrigin entirely; login:32 and logout:97 both call it); session.ts:248 cookie attributes; api.ts:75-131 would reject the sibling Origin if called; effect ceiling = forced rotation churn + possible GoTrue session-family revocation (forced logout) — no token disclosure (httpOnly, no CORS, tokens never in body).

**Exact blockers**: (a) production hostname/registrable domain + existence of an untrusted sibling-subdomain origin (Vercel default *.vercel.app is PSL-protected → vector void; custom domain with sibling content → enabled); (b) GoTrue refresh-token reuse interval for the owner's project (repo documents a prior lenient observation at readiness-report:173, flagged as config-dependent); (c) source-only run policy.

**Resolution plans**: LOCAL (dummy Supabase project only) — hosts-file map app.local.test + attacker.local.test (same registrable domain, 'test' not on PSL), login on app.local.test:3000, then from attacker.local.test page: fetch('http://app.local.test:3000/api/auth/refresh', {method:'POST', credentials:'include'}) — observe cookie attachment and whether burst rotations ever trigger family revocation. DEPLOYMENT (owner-observed) — record production hostname + registrable domain; enumerate sibling subdomains for untrusted content; read GoTrue reuse interval from dashboard; before shipping the fix (assertSameOrigin as first statement of refresh), confirm from access logs that legitimate refreshes always carry Origin/Referer.

## 2. src/lib/api.ts:assertSameOrigin-origin-scheme-ignored

**Claimed root cause**: assertSameOrigin reduces Origin (line 95) and the Referer fallback (line 102) to the host component only; both comparisons (117 vs x-forwarded-host/host, 125 vs appUrl host) are host-only; no code path validates the scheme, so Origin 'http://<host>' passes for an app served at 'https://<host>' (WHATWG URL drops default ports, so both reduce to the same host string).

**Verified evidence**: source-level acceptance of cross-scheme same-host Origin is established (every admin mutation passes the check); remaining defenses are ambient: SameSite=Lax cookie attachment and Sec-Fetch-Site, both of which treat the pair as cross-site only on schemeful-same-site engines (all current mainstream browsers do).

**Exact blockers**: (a) whether plain HTTP on the production hostname can serve non-redirecting content (Vercel expected to 301/308 but not source-visible; self-host path has no TLS config; MitM alternative where HSTS unpinned); (b) the admin's actual browser matrix (legacy engines without schemeful same-site: Chrome <86, Firefox <90, Safari <16.4-era); (c) Sec-Fetch-Site value on such engines.

**Resolution plans**: LOCAL — unit-test fixture: NextRequest POST {host:'app.example', origin:'http://app.example', cookie:'tsundoku_at=t'} currently does NOT throw (source-established); fix design verified: compare new URL(origin).origin against x-forwarded-proto+host canonical origin, fail-closed on missing proto header (with caveats for TLS-terminating proxies and the appUrl default). DEPLOYMENT — owner: curl -sI http://<production-host>/ must 301/308 to https, no content on port 80, HSTS present on https origin; record admin browser matrix.

## 3. src/app/api/uploads/abort/route.ts/PENDING-filter-non-atomic-with-R2-delete

**Claimed root cause**: abort's PENDING-only filter (findMany :40-44) and its destructive effect (safeDeleteObjects :52 → R2 DeleteObjects; deleteMany :53-57 with no status predicate) are separate unsynchronized awaits with an R2 round-trip between them; a concurrent finalize (B1 accepts PENDING → B2 HeadObject → B3 commits CONFIRMED + page row) landing between selection and destruction has its just-CONFIRMED object destroyed and its storage row removed while the page references it. Wider variant: abort's R2 delete landing between finalize's B2 and B3 — B3's blind upsert re-creates the row as CONFIRMED pointing at the deleted object.

**Verified evidence**: no transaction/lock/conditional update spans check and effect; Page.objectKey and Manga.coverImageKey have no FK to StorageObject; the upload UI's unmount cleanup (upload-view.tsx:312-320, settledRef only after finalize resolves :530) fires abortAll concurrent with an in-flight finalize without adversarial tooling; cover finalize is an equivalent racing writer; existing test covers only the sequential case.

**Exact blockers**: the harmful interleaving requires a repeatable runtime schedule (source-only run; integration harness needs live Supabase+R2); production scheduling/window widths are runtime facts.

**Resolution plans**: LOCAL (dev harness, dummy data) — instrument R2 DeleteObjects with a configurable delay; fire finalize + abort concurrently for one presigned key; assert the corrupted state (finalize 201, page row references K, HeadObject(K) 404, storage row gone). Then apply the two-sided fix — (1) abort claims rows atomically: per key updateMany({objectKey:k, status:'PENDING'} → DELETE_PENDING) before any R2 deletion, only delete claimed keys (a status predicate on the final deleteMany alone is insufficient — the R2 object is destroyed first); (2) finalize B3 replaces the blind upsert with a conditional confirm that throws on DELETE_PENDING/missing rows — and re-run the same interleaving. DEPLOYMENT (owner, read-only) — query for dangling references (page rows/cover keys without storage rows or with HeadObject 404); log abort's deleteMany-count vs selected-count delta.

## 4. migrations.profiles-self-insert-policy-email-not-pinned

**Claimed root cause**: the RLS 'profiles self insert' policy checks only auth.uid() = id; the globally-unique email column is attacker-chosen; no trigger binds profiles.email to auth.users. An authenticated non-admin inserting {own uuid, ADMIN_EMAIL} before the admin's first login makes ensureProfile's create branch hit unique(email) P2002 → 409 on every admin login (awaited before cookies at login:141) — persistent lockout with no app-path recovery (no code deletes foreign profile rows). Variant: the migration tool's Prefer: resolution=ignore-duplicates silently skips a colliding admin profile row while its '>= expected' count check still passes.

**Verified evidence**: policy text and unique constraint; ensureProfile is the only profile write; bootstrap-admin creates no profiles row (attack window open until first login); verify-rls never tests the profiles self-insert policy; ADMIN_EMAIL is a documented constant externally confirmable via the login enumeration oracle (confirmed finding); dev local-admin profile id is non-UUID so the migration tool cannot pre-create the admin's production profile row.

**Exact blockers**: (a) existence of any second authenticated Supabase user (signup-disable is a manual dashboard step; verify-rls itself mints credentialed non-admin users); (b) whether 0001_init.sql is applied in production PG; (c) PostgREST default grants exposing public.profiles to the authenticated role; (d) timing state — the lockout requires the insert while no admin profile row exists (if the owner has logged in once, the upsert takes the update branch and nothing fails).

**Resolution plans**: LOCAL — SQLite unique-email half: insert a profile row with the admin's email under a different id, call ensureProfile(admin), observe P2002 → 409. DEPLOYMENT (STAGING project only) — apply the migration; non-admin user POSTs {own uuid, ADMIN_EMAIL} to /rest/v1/profiles with publishable key + user Bearer (expect 201); real admin login then 409s with no cookies; recover by deleting the dummy auth user (FK on delete cascade) and confirm login succeeds; reproduce the migration-tool silent-skip variant. In production record: signup toggle state, non-admin user list (incl. leftover verify-rls temp users), migration-applied state, admin-profile-row existence. Fix once validated: pin the policy (`with check (auth.uid() = id AND email = auth.jwt() ->> 'email')` or an auth.users-synced trigger) and/or pre-create the admin's profile row at bootstrap time.

## 5. Caddyfile:XTransformPort-localhost-port-proxy

**Claimed root cause**: the committed repo-root Caddyfile binds :81 on all interfaces and forwards any request with ?XTransformPort=<port> to localhost:<port> (presence-only matcher, no allowlist/auth/method restriction); .zscripts/start.sh:145 runs it as the sandbox deploy's main process and .zscripts/build.sh:151 ships it in every tarball — a loopback SSRF proxy for any client that can reach :81.

**Verified evidence**: Caddyfile:1-13 text; start.sh/build.sh wiring; the harness design pattern (examples/websocket on :3003 reached via the same rule); the owner-declared Vercel production flow never executes these files; in the committed tree the only loopback service is the app on :3000.

**Exact blockers**: whether the sandbox :81 listener is reachable beyond the owner's authenticated preview session (platform network fact); which loopback services exist on the live host; whether the .zscripts deploy path is used beyond the private sandbox preview.

**Resolution plans**: LOCAL — fixture: copy the Caddyfile to an unprivileged port, run two dummy 127.0.0.1-only HTTP servers, curl 'http://127.0.0.1:8081/?XTransformPort=9999' (GET+POST) and observe the internal marker — proves the loopback-boundary crossing with attacker-chosen port. DEPLOYMENT (owner-observed, non-destructive) — from a non-owner vantage, attempt the transform-port URL against a deliberately started dummy loopback service; on the runner, ss -ltnp to enumerate reachable listeners. Treat the Caddyfile as scaffolding to remove or restrict (explicit port allowlist) before any self-hosted reuse of this branch; the Vercel path is unaffected.
